# westc 无卡迁移时发现的退出竞态

首次服务器完整 234 项 CPU 测试有一项失败：0.3 秒已到，但用于断言子进程启动的 order.txt 尚不存在。实例 CPU quota 为 50,000/100,000 微秒，即半核；初次测试同时存在数据传输，0.3 秒不能保证启动 Python 子进程。

单项复查发现另一种失败：status.json 仍是 running，Popen 对象警告子进程未回收。后续捕获显示，执行器的 monotonic 截止时间和 SIGALRM 的到达非常接近。前者可以先同步抛出 TimeoutError；若 SIGALRM 随后在异常处理入口、取消计时器之前到达，信号处理器会再次抛出异常，跳过原来的回收和状态更新。

新增 `test_alarm_during_exception_cleanup_cannot_skip_child_reaping` 在真实 Popen 创建后、异常处理取消计时器之前注入 SIGALRM：原 153953a 确定性失败，状态仍为 running。测试 finally 主动清理子进程，不留下诊断进程。失败日志见 local-cleanup-regression-before.log。

修复：在已有异常处理期间暂存信号，不用异步异常覆盖正在处理的异常；在下一阶段启动和最终分析后检查暂存的信号。保留已有 Popen 锁保护和 3,600 秒实际总预算。实际模型、数据划分、配置、损失、训练预算和继续条件不变。

两项实际 alarm 测试改为先等到目标执行位置：CPU 校验进入后、真实子进程和孙进程就绪后，才设置测试使用的短 alarm。仍使用真实 SIGALRM 和进程组，检查及时终止、直接子进程已回收、孙进程没有延迟写入，避免用启动速度决定测试结果。独立的累计预算测试仍检验一整条队列共用预算。

修复后本机 20 项执行器测试及完整 235 项 CPU 测试通过。服务器结果单独记录，未将首轮失败写成通过。固定源码 1a3830754dbffa87f06348e842e68a07fb4054c7；发布仓库对应 cherry-pick e59753a。训练源码 SHA256 仍为 38d9afc3cdc0440695cb5eca5c59069f73ace1aba4478d5afc5b656050911840。
